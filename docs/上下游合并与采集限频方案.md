# 上下游合并与采集限频方案（2026-11-23）

基线：上游 4.4.6（84 项测试本机通过，40 秒）+ 下游 4.2.5-agent.17.3-auto（agent 86 / addons 59 通过）。
存档实测：693 MB，`_data` 209 MB，`manifest.json` **5.4 MB**，10505 帖，journal 15 个文件 37 MB。

---

## 一、合并形态：先定这个，其余都跟着变

### 事实

- 上游 4.4.6 的 `poster.js`、`api.js`、`alerts.js` 与下游内嵌的 4.2.5 **逐字节相同**，`sw.js` 也相同。
  也就是说：这三个下游补丁可以原样套到 4.4.6 上，扩展模块接入点没变。
- 上游新增 `archive-data.js`（机读存档发布端），下游没有；下游的读取端是 `agent/archive-data.mjs`。
- 权限列表完全一致，合并不会触发新的授权提示。

### 两种形态

| | A. 一份代码，两种角色（推荐） | B. 单浏览器单实例 |
|---|---|---|
| 部署 | Edge 装采集端，Chrome 装回复端，同一份代码用角色开关区分 | 一个浏览器全干 |
| 账号/指纹 | 保持隔离（你原来的刻意安排） | 采集与发帖同一账号、同一指纹 |
| 写存档 | 只有采集端允许写，回复端强制只读 | 单一写入方，天然不抢租约 |
| 风控 | 读帖与发帖行为分开，风险不叠加 | 读帖+发帖同一 IP/账号，风险叠加 |
| 延迟 | 回复端仍需轮询存档（可优化，见第三节） | 采集完成即可直接触发拟稿，秒级 |
| 工作量 | 中 | 中，但风险不可控 |

**建议 A。** 合并的意义是「一个版本、一起维护、界面统一」，不必牺牲指纹隔离。角色开关落在设置里：
`role: 'collector' | 'responder'`，采集端才启用 background 采集与 `_data/writer.json` 租约，回复端在启动时断言自己不是写入方。

如果坚持 B，则必须接受：论坛把读帖与发帖归到同一账号，一旦被风控，发帖也会一起停。

## 二、六条限频需求的差距分析

| # | 需求 | 4.4.6 现状 | 要做的事 |
|---|---|---|---|
| 1 | 巡查 5～10 分钟 | 默认 **10～20 分钟**，可设范围 | 改默认值与设置项下限 |
| 1 | 单帖间隔 20～30 秒 + 浮动 | **`MIN_GAP=3000, MAX_GAP=6000`**，即 3～6 秒 | 改常量，并按帖页数分档（长帖更长） |
| 1 | 每小时请求上限 | **无** | 新增计数器，到顶自动歇到下个整点 |
| 2 | 回复数/最后回复时间没变就不点进去 | 已有 `noNewSinceCheck`，但**只比回复数** | 补「最后回复时间」比较；两者都未变才跳过 |
| 2 | 长帖只从上次页往后采 | 已有 `startPage` / `toEnd` / `lastPage` 增量 | 基本可用；需核对翻页上限与「已核对标记」的交互 |
| 3 | 503/验证页立刻全停 + 15/30/60 递增 | 现在**单页退避重试**几次，再把**该任务**冷却；其它任务继续跑 | 改为全局熔断：置 `haltCollect`，按 15→30→60 分钟递增解锁 |
| 4 | waiting_human 立即通知 | 有 `chrome.notifications` 系统通知 | 增加 Telegram 推送（合并后可直接用现有 bot） |
| 5 | 队列优先级 | **无**；队列是 FIFO，当前积压 44 条 | 新增优先级：自己的帖 > 观察名单参与的帖 > 其它 |
| 6 | 状态置顶 + 超 1 小时标红 | 有 `lastCaptureAt`，但弹窗顶部没展示 | 弹窗顶部显示「最后成功采集 + 距今」；>1h 标红并配文字 |

补充：`control-tools.js` 的「最近事件」用 `toLocaleString()`，**本身带日期**；你看到只有时间，是因为事件条目里存的可能是格式化过的短时间串。合并时统一改成 `YYYY/MM/DD HH:mm +08:00`，与下游一致。

## 三、性能：清单 5.4 MB / 分钟，是当前最大的浪费

下游每 60 秒 `scan()` 一次：读 5.4 MB 清单 + `JSON.parse` + 遍历 10505 条校验。
一天约 **7.8 GB** 磁盘读，且每次都占 CPU。

协议 7.6 已经给了正确做法，下游没实现：

1. 正常情况只读 `journal/*.jsonl` 里 `cursor < seq ≤ manifest.seq` 的行（增量，通常几 KB）；
2. 只有四种情况才全量对账：`sourceId` 变、`generation` 变、`manifest.seq < cursor`、`cursor+1 < journal.firstSeq`（日志缺口）；
3. 内容是否变化用 `mdSha256` 判断，`jsonSha256` 只用于确认读完整。

改造后：稳态下每轮读几 KB 而不是 5.4 MB，延迟也从「最多 60 秒」降到「下一轮即到」。
若采用形态 A，回复端仍跨浏览器，这条优化就是主要收益；若采用形态 B，可以直接事件驱动，连轮询都不需要。

## 四、合并的文件级步骤

以 4.4.6 为基线，顺序不能颠倒：

1. **基线**：`extension/` ← 4.4.6 全部 36 个文件（含 `archive-data.js`）。
2. **补下游模块**：覆盖 `extension/addons/`（22 个文件，含新 `timefmt.js`）。
3. **打补丁**：`patches/poster.js`、`patches/api.js`、`patches/alerts.js` 原样覆盖
   （已验证三者与 4.2.5 同字节，补丁不会冲突）。
4. **改 LocalMode**：`extension/addons/local-mode.js` 从「强制暂停采集 + 强制关闭自动发表」
   改为「按 role 决定」：
   - `collector`：采集开、回复关；
   - `responder`：采集关、回复开；
   - 启动时若 `role==='responder'`，断言自己不是 `_data/writer.json` 的持有者。
5. **界面合并**：之前裁掉的 `popup.*`、`options.*`、`control.html`、`control-tools.js`
   **要恢复**（采集端需要），但要重做视觉与信息层级：
   - 一个入口（popup）顶部放状态条：最后成功采集时间、距今、队列长度、是否熔断；
   - 采集工作台（control.html）与回复工作台（addons/workbench.html）做成同一页面的两个标签，
     或 popup 里两个按钮分流。
6. **清单与校验**：重新生成 `upstream-lock.json`（48 → 新文件集，含 `archive-data.js`），
   `scripts/verify-upstream.mjs` 与 `package-local.mjs` 的排除清单同步调整。
7. **版本号**：`manifest.version` 与 `version_name` **都要改**（Edge 显示 `version_name`），
   建议 `5.0.0` / `5.0.0-merged.1`。
8. **测试**：上游 `test/` 84 项 + 下游 `test-addons/` 59 项 + `agent/` 86 项，统一一个入口跑完；
   上游测试里的 poster 相关用例要跑在**打过补丁**的扩展上（下游那 12 条同理）。

## 五、限频改造的具体落点

### 5.1 间隔与上限（需求 1）

```js
// background.js
const MIN_GAP = 20000, MAX_GAP = 30000;          // 20~30 秒
const GAP_PER_PAGE = 400;                         // 每多一页再加一点
const HOURLY_BUDGET = 300;                        // 每小时请求上限，到顶歇到下个整点
```

- 巡查：`sweepMin/sweepMax` 默认改 `5/10`，设置页下限卡 5。
- 每发一个请求前检查 `hourlyCount`，超限则 `alarms.create('resume', {when: 下一个整点})`。

### 5.2 只采变化（需求 2）

列表页已有 `replies` 与 `lastReplyAt`（若没有，需从 `parser.js` 的列表解析补字段）。
跳过条件改为**两者都未变**：

```js
const unchanged = rec && rec.checkedReplies === replies && rec.checkedLastReply === lastReply;
```

注意：4.4.3 提到论坛限制历史帖（2017～2025 约 1325 帖只能看到 1 楼），这类帖子不能因为
「回复数没变」就当作已完整——保留 `lastFailure` 判断优先于跳过。

### 5.3 全局熔断（需求 3）

现状是「单页重试 → 单任务冷却」，多个任务会继续撞。改为：

```
检测到 503 或验证页 → 立即 haltCollect=true，清空进行中任务（不重试）
等待 15 分钟 → 试读一页 → 仍被挡 → 30 分钟 → 仍被挡 → 60 分钟 → 之后固定 60 分钟
任一页成功 → 重置阶梯，恢复采集
```

关键点：**熔断期间队列不动、不重试、不新增请求**。这是「越撞越严」的直接解法。

### 5.4 waiting_human 通知（需求 4）

- 系统通知保留；
- 新增 Telegram：合并后扩展已能调用本地 Agent，直接 `POST /track-notify` 或复用现有
  `notify()` 通道推给梦溪·回声机器人；
- 通知内容带帖子编号、原因（论坛原话）、以及「点掉验证后会自动继续」。

### 5.5 队列优先级（需求 5）

队列项加 `priority`：

| 优先级 | 来源 |
|---|---|
| 3 | 我自己的帖子（`myName` 发的帖） |
| 2 | 观察名单用户参与过的帖 |
| 1 | 手动「立即采集」 |
| 0 | 巡查发现的一般更新 |

`nextFromQueue()` 取最大优先级，同优先级 FIFO。当前积压 44 条，改造后重要帖子不会排在最后。

### 5.6 状态置顶（需求 6）

popup 顶部状态条：

```
最后成功采集：2026/11/23 06:52 +08:00（12 分钟前）
队列 44 · 本轮已用 137/300 次请求 · 熔断：无
```

超过 1 小时未成功：整条标红 + 文字「超过 1 小时没有新数据，可能是被风控或验证挡住」。
不只靠颜色——色弱用户与截图转发都要能看懂。

## 六、明天建议的执行顺序

1. **合并骨架**（1～2 小时）：4.4.6 + addons + 三个补丁，能加载、能采集、能回复，跑通 84+59 测试。
2. **限频四件套**（2～3 小时）：间隔、每小时上限、只采变化、全局熔断。这四项直接对着风控。
3. **通知与优先级**（1～2 小时）：waiting_human 推 Telegram、队列优先级。
4. **状态置顶 + 事件时间统一**（1 小时）。
5. **journal 增量读取**（1～2 小时）：先做兼容（读不到 journal 自动退回全量），再做默认。
6. **回归**：上游 84 + 下游 59 + agent 86；用真实存档跑一次 10 分钟观察请求数与 CPU。

## 七、风险

| 风险 | 处理 |
|---|---|
| 两个实例同时写存档 | 角色开关 + 租约检查；回复端启动即断言只读 |
| 恢复上游界面后，之前裁掉的 11 个文件回来 | 只恢复采集必需的（popup/options/control/control-tools），posting 系列仍可不要 |
| 上游测试跑在下游补丁上可能冲突 | 先跑原始 4.4.6 测试，再跑打补丁后的，分开定位 |
| 每小时上限设太小会拖慢首次全量 | 首次全量与日常巡查用不同预算，全量单独开关 |
| journal 增量实现有 bug 会漏帖 | 保留全量对账开关；对账结果与 journal 结果做一致性自检 |
